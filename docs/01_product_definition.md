# RobotOps AI 产品定义

## 1. 背景

机器人研发测试阶段，测试人员通常会在飞书或缺陷系统中提交 Bug。组长将 Bug 分配给对应开发后，开发工程师需要根据问题描述、发生时间、机器人类型和完整日志包进行分析。

当前排障方式存在明显问题：

- 日志分散在多个模块目录中，例如 `interaction`、`mc`、`agent`、`hal_camera`、`sm`、`hds`。
- 工程师需要手动解压、搜索、对齐时间线。
- 很多问题需要结合源码逻辑理解，不是只看 ERROR 就能判断。
- 历史 Bug 经验难以沉淀，新人排障依赖老工程师经验。

RobotOps AI 第一阶段用于把这一过程平台化和半自动化。

当机器人产品交付并部署到客户现场后，平台还需要从研发诊断工具演进为部署运维平台，支持机器人在线状态、模块心跳、事件告警、远程日志和工单诊断。

## 2. 用户角色

### 2.1 测试人员

工作内容：

- 复现机器人问题。
- 提交 Bug 描述、发生时间、机器人类型。
- 上传完整日志包。

痛点：

- 不知道哪些日志对开发有用。
- Bug 描述和日志经常缺少关联。
- 反馈后等待开发分析周期较长。

需求：

- 按模板提交 Bug。
- 上传 `robot_日期.zip` 日志包。
- 查看诊断进度和结论。

### 2.2 开发工程师

工作内容：

- 分析 interaction、mc、agent、hal、sm、hds 等模块日志。
- 结合源码判断问题原因。
- 给出修复建议或责任模块。

痛点：

- 多模块日志人工检索耗时。
- 需要反复 grep 日志和源码。
- 同类问题重复分析。

需求：

- 根据 Bug 时间自动提取前后日志上下文。
- 自动定位日志对应源码位置。
- 生成可编辑的 AI 诊断报告。

### 2.3 组长/负责人

工作内容：

- 分配 Bug。
- 判断问题责任模块。
- 追踪修复进度。

痛点：

- 难以快速判断 Bug 属于哪个模块。
- 历史问题缺少结构化统计。

需求：

- 查看 Bug 分布、模块故障排行。
- 查看诊断报告和处理记录。

### 2.4 现场支持工程师

工作内容：

- 接收客户现场问题反馈。
- 查看机器人近期状态、日志和故障码。
- 判断是否需要远程处理、升级版本或派单维修。

痛点：

- 客户描述通常不完整。
- 现场问题很难复现。
- 研发日志和现场工单之间缺少关联。

需求：

- 查看机器人在线状态和最近心跳。
- 查看各模块近期告警。
- 查询问题发生前后的远程日志。
- 复用研发阶段沉淀的历史 Bug 诊断案例。

## 3. 核心流程

### 3.1 研发测试阶段

```text
测试提交 Bug
  ↓
上传完整日志包
  ↓
系统识别模块日志
  ↓
按发生时间抽取上下文
  ↓
Agent 检索源码和历史案例
  ↓
生成诊断报告
  ↓
开发确认并沉淀知识库
```

### 3.2 部署运维阶段

```text
客户现场机器人上报心跳/状态/事件
  ↓
平台检测模块异常或客户提交工单
  ↓
系统拉取近期关键日志和模块状态
  ↓
Agent 结合历史案例和源码知识生成远程诊断建议
  ↓
现场支持工程师确认处理方案
```

## 4. MVP 范围

必须实现：

- 手动创建 Bug 单。
- 上传或导入日志包。
- 识别模块目录和日志文件。
- 解析日志等级、时间、模块名和原始内容。
- 查询指定时间窗口内的多模块日志。
- Python Agent 生成诊断报告。
- 接口和表结构预留机器人实时状态、模块心跳、事件告警字段。

暂不实现：

- 飞书 OpenAPI 自动同步。
- 真实机器人远程在线状态采集。
- 权限审批流。
- 自动修改代码。
- 大规模集群部署。
