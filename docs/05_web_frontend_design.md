# Web 前端设计

## 1. 前端定位

RobotOps AI 主前端采用 Web 管理台，不再使用 Qt。

前端定位：

```text
机器人运维与诊断 Web 工作台
```

Web 前端需要服务两个阶段：

| 阶段 | 前端重点 |
|---|---|
| 研发测试阶段 | Bug 分析、日志包上传、多模块日志检索、AI 诊断报告、源码证据 |
| 售后运维阶段 | 机器人资产、模块实时状态、告警事件、售后工单、远程诊断 |

## 2. 为什么不用 Qt

Qt 更适合：

- 机器人本体调试工具
- 内部工程师本地工具
- 需要直接访问硬件或本地环境的桌面程序

RobotOps AI 是平台型系统，更适合 Web：

- 方便多人访问。
- 方便和飞书 Bug、工单系统、后端服务集成。
- 方便展示仪表盘、时间线、日志检索和诊断报告。
- 更像企业真实运维平台。
- 后续部署到服务器后，测试、开发、售后都可以通过浏览器使用。

## 3. 风格参考

前端产品组织方式参考 `qinshihu/itops-agent-platform` 这类运维 Agent 平台。

可借鉴点：

- 首页先展示平台核心闭环，而不是堆技术。
- 工作台按运维流程组织页面。
- 用卡片和状态区展示任务、告警、诊断进度。
- 强调 Agent 分析过程、证据和结果。
- 让用户一眼看到“现在有哪些问题、系统正在分析什么、结论是什么”。

注意：

- 不照搬它的业务，因为它面向 IT 运维。
- RobotOps AI 面向机器人研发测试和售后诊断。
- 页面内容必须围绕 `interaction / mc / agent / hal / sm / hds` 多模块诊断。

## 4. 推荐技术栈

前端建议二选一：

```text
React + TypeScript + Vite
Vue 3 + TypeScript + Vite
```

UI 组件库建议：

```text
Ant Design / Arco Design / Naive UI
```

如果希望更像企业后台，推荐：

```text
React + TypeScript + Vite + Ant Design
```

前端不直接访问：

- MySQL
- Redis
- Elasticsearch
- RabbitMQ
- Milvus

前端只调用后端 HTTP JSON 接口。

## 6. 核心页面

### 6.1 总览仪表盘

目标：

- 展示平台当前诊断和运维概况。

内容：

- 今日新增 Bug 数
- 待诊断 Bug 数
- 诊断完成数
- 高风险问题数
- 最近上传日志包
- 最近 AI 诊断报告
- 售后阶段预留机器人在线数、模块异常数、告警数

### 6.2 Bug 分析页

目标：

- 作为研发阶段核心入口。

表单字段：

```text
Bug 标题
Bug 描述
机器人类型：T 型 / Q 型
问题模块：interaction / mc / agent / hal_camera / sm / hds
发生时间
软件版本 / 分支 / commit
日志包
源码仓库
```

操作：

- 创建 Bug
- 上传日志包
- 启动 AI 诊断
- 查看诊断结果
- 标记责任模块
- 保存为历史案例

### 6.3 日志包页

目标：

- 管理测试上传的完整日志包。

内容：

- 日志包名称，例如 `robot_20260730.zip`
- 关联 Bug
- 上传时间
- 解析状态
- 识别出的模块列表
- 日志文件数量
- 解析错误

支持操作：

- 上传日志包
- 重新解析
- 查看解压结构
- 跳转日志检索

### 6.4 多模块日志检索页

目标：

- 替代人工在本地 grep 多个模块日志。

筛选条件：

```text
Bug ID
模块名
日志级别
关键词
时间范围
文件名
trace_id / task_id / session_id
```

展示字段：

```text
时间
模块
级别
文件
行号
消息
原始日志
```

关键能力：

- 查看发生时间前后 N 分钟日志。
- 按模块过滤。
- 高亮 ERROR/WARN。
- 从日志跳转到源码证据。

### 6.5 时间线分析页

目标：

- 把多模块日志按时间排序，展示 Bug 前后的调用链。

示例：

```text
15:32:10 hal_touch 上报 touch event
15:32:10 interaction 收到 touch event
15:32:10 interaction 检查 self check
15:32:10 interaction 检查当前 action
15:32:10 interaction 拦截 touch task
15:32:11 mc 仍处于 PASSIVE_DEFAULT
```

用途：

- 判断请求有没有到 interaction。
- 判断 interaction 有没有继续调用底层。
- 判断失败发生在哪个阶段。

### 6.6 AI 诊断报告页

目标：

- 展示 Agent 的结构化分析结果。

报告结构：

```text
问题现象
诊断摘要
疑似责任模块
可能原因
日志证据
源码证据
建议处理方向
置信度
需要人工确认的问题
```

要求：

- 不能只显示一段 AI 文本。
- 必须展示证据。
- 必须能追溯到日志行和源码文件。
- 证据不足时要明确显示低置信度。

### 6.7 源码证据视图

目标：

- 展示日志关键句对应的源码位置。

内容：

- 仓库名
- 分支 / commit
- 文件路径
- 函数名
- 匹配日志语句
- 附近代码片段
- Agent 分析说明

第一版可以只做只读展示，不做在线编辑。

### 6.8 机器人资产页

售后阶段使用。

字段：

```text
robot_sn
robot_type
software_version
customer
site
online_status
last_heartbeat_at
```

研发阶段如果没有机器人编号，可以暂不作为主入口。

### 6.9 模块状态页

售后阶段使用。

模块：

```text
agent
interaction
mc
hal_camera
hal_audio
hal_touch
bms
sm
hds
```

展示：

- 模块在线状态
- 最近心跳
- 最近 ERROR/WARN
- 当前状态摘要
- 关联告警

## 7. 交互原则

- 这是运维和诊断工作台，不是营销页。
- 第一屏应该直接进入工作台，不做大段宣传 hero。
- 页面要强调状态、证据、流程和结论。
- 表格、筛选、时间线、详情抽屉、状态标签优先。
- AI 诊断结果必须可解释，不能只展示自然语言。
- 日志和源码证据必须能复制、定位和追溯。
- 时间统一显示本地时间，同时保留原始时间戳。

## 8. 与后端协作

前端只依赖后端 API，不依赖数据库结构。

接口来源：

```text
proto/
后端 HTTP JSON 文档
```

错误处理统一：

- 后端业务失败：展示 `response.message`。
- 网络失败：提示服务不可用。
- 解析失败：展示响应格式错误。
- AI 诊断失败：保留任务状态，允许重试。

## 9. MVP 开发顺序

第一批页面：

1. 总览
2. Bug 分析
3. 日志包
4. 日志检索
5. AI 诊断报告

第二批页面：

1. 时间线分析
2. 源码证据
3. 知识库

第三批页面：

1. 机器人资产
2. 模块状态
3. 告警事件
4. 售后工单
